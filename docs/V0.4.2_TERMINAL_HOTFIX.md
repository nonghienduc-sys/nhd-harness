# v0.4.2 Terminal Hotfix

Date: 2026-09-13

## Incident

Production TerminalService reached its hard concurrency limit of three active runs even though the PowerShell launcher processes had already exited.

The stuck runs were created by v0.5 staging launchers that used `Start-Process` to start long-lived Node processes on staging ports `39110`, `39112`, and `39113`.

The old TerminalService waited for Node child-process `close` before removing a run from the in-memory concurrency map. On Windows, a descendant started by PowerShell can inherit stdout/stderr handles. In that state:

- PowerShell launcher exits,
- descendant keeps inherited handles open,
- Node child-process `exit` occurs but `close` may be delayed,
- TerminalService keeps the run in `running`,
- all three concurrency slots can become permanently occupied.

`terminal_cancel` could request `taskkill`, but the old implementation still depended on the delayed close lifecycle to remove the map entry.

## Recovery without restarting production

The three staging listeners were identified by local port, PID and full command line before any process was stopped:

- port `39110` -> staging `server.js`,
- port `39112` -> browser staging `server.js`,
- port `39113` -> staging `office-companion.js`.

Production port `39100` was explicitly excluded.

After stopping only those three verified staging processes, inherited pipe handles closed and the old TerminalService released all three slots. A normal terminal command then completed successfully, proving production could be recovered without restarting MCP.

## Code changes

Production v0.4.2 backports only the TerminalService artifacts:

- `dist/terminal.js`
- `dist/terminal.d.ts`
- `dist/terminal.js.map`

The corresponding source changes live in `src/terminal.ts`.

### 1. Exit-first completion

A terminal run now finishes shortly after the PowerShell launcher emits `exit` instead of waiting indefinitely for `close`.

A short grace period allows normal final stdout/stderr draining, then the service destroys the launcher pipe objects and releases the concurrency slot.

### 2. Stale PID pruning

Before enforcing the three-run concurrency limit, and while listing active runs, TerminalService checks whether each launcher PID still exists.

Dead launcher entries are removed automatically and audited as stale-pruned runs.

### 3. Cancel reconciliation

After `taskkill`, TerminalService verifies whether the launcher PID is still alive. If the PID is gone, the run is removed from the concurrency map even if a descendant-held pipe prevents the old close lifecycle from completing normally.

## Cutover failure and corrected deployment architecture

The first v0.4.2 cutover attempt used a PowerShell script launched by TerminalService. That script attempted to stop the same MCP/Electron runtime that owned its process tree.

Observed outcome:

1. preflight passed,
2. backup completed,
3. package manifest was bumped to `0.4.2`,
4. parent MCP runtime was stopped,
5. cutover script died with its parent before TerminalService artifacts could be copied.

This temporarily left a misleading state: health reported v0.4.2 from the manifest, but production `terminal.js` still had the old hash.

The successful completion used a process created through Windows `Win32_Process`/WMI. That helper was owned independently of the MCP process tree, so it survived the MCP restart.

The helper performed this order:

1. verify current health, tunnel and 53-tool baseline,
2. create safety backup,
3. copy and hash-verify the three TerminalService artifacts **before** stopping MCP,
4. stop the old MCP/tunnel runtime,
5. start Electron with `ELECTRON_RUN_AS_NODE` removed,
6. wait for v0.4.2 health,
7. wait for Cloudflare Tunnel Online,
8. verify 53-tool baseline and reject any v0.5 Browser/Office Live Write leakage,
9. verify production TerminalService hashes,
10. write `v042-last-result.json`.

The old in-process cutover script `scripts/v042-terminal-cutover.ps1` is intentionally disabled and must not be restored to its previous self-restart behavior.

## Deployment rule going forward

A process must never be responsible for stopping the parent runtime that owns that process unless another independent supervisor already owns restart and rollback.

For future MCP production cutovers, use one of:

- an independently supervised Windows helper process,
- a Windows service/scheduled supervisor,
- another external deployment controller.

Do not rely on a TerminalService child process to survive termination of its own MCP parent.
