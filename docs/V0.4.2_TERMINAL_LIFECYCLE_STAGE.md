# v0.4.2 Terminal Lifecycle Stage

Date: 2026-09-13
Status: **STAGING ONLY — NOT DEPLOYED TO PRODUCTION**

## Problem observed

Production `TerminalService` in v0.4.1 tracks active runs in an in-memory `running` map and removes a run only from the Node child-process `close` handler.

Three staging launcher runs remained visible indefinitely in the dashboard even though their PowerShell launcher PIDs no longer existed. The common pattern was a launcher that started a long-lived background child. On Windows, a descendant may keep inherited stdout/stderr handles open after the PowerShell launcher has already exited. In that situation:

1. PowerShell launcher exits.
2. Node receives `exit` for the launcher.
3. A descendant still owns inherited pipe handles.
4. Node does not receive `close` promptly.
5. `TerminalService.running` still contains the run.
6. The fixed concurrency limit of 3 is exhausted by ghost records.
7. New `terminal_execute` calls are rejected even though the original launcher processes are gone.

This is separate from the Cloudflare tunnel incident fixed in v0.4.1.

## Staged design

`src/terminal.ts` now separates **concurrency-slot lifetime** from **stdio-drain lifetime**.

### On launcher `exit`

- release the run from the `running` map immediately;
- stop counting the launcher against the 3-run concurrency limit;
- retain stdout/stderr listeners briefly so final buffered output is not lost;
- wait for normal `close` for up to `drainGraceMs` (default 500 ms).

### On normal `close`

- finalize immediately;
- preserve final stdout/stderr accumulated during the drain window;
- cancel the drain timer.

### If `close` never arrives

- finalize after `drainGraceMs`;
- prevent a detached/background descendant from keeping an MCP terminal call and slot alive indefinitely.

### Safety behavior retained

- command preview/hash binding remains unchanged;
- critical confirmation remains unchanged;
- timeout still kills the launcher process tree;
- cancel still requires an active tracked run;
- stdout/stderr redaction and output limits remain unchanged;
- Emergency Stop / terminal owner switch remain authoritative.

## Regression tests prepared

`test/terminal-lifecycle.test.mjs` contains two focused cases:

1. launcher emits `exit` but never emits `close` — the slot must be released immediately and execution must finalize after a short drain period;
2. launcher emits `exit`, produces a final stdout tail, then emits `close` — the final output must be preserved and execution must complete without waiting for the full grace timeout.

The test uses an injected fake child process and `maxConcurrentRuns=1` so slot-release behavior is deterministic.

## Current blocker

The production v0.4.1 process still holds three pre-fix ghost run records in RAM. Because the production terminal concurrency guard sees 3/3 active entries, the workstation cannot currently run the staging build/test command through its own Terminal MCP tool.

Cancelling a ghost run cannot fully remove it in v0.4.1 because the old implementation removes the map entry only from `close`. The launcher PID is already gone, so there is no remaining launcher process whose termination can trigger the missing lifecycle transition.

## Deployment gate

Do **not** deploy this patch solely from source inspection.

Before production deployment, complete all of the following:

1. obtain a clean TerminalService runtime (normally after a controlled MCP restart or natural app restart);
2. run `scripts\test-terminal-stage.ps1`;
3. run the complete existing regression suite against the staged build;
4. verify no staging server is bound to production port 39100;
5. back up production `dist` and manifests;
6. deploy only after staging tests pass;
7. after restart verify:
   - production health,
   - tunnel Online,
   - terminal running count returns to 0 after launcher exit,
   - background `Start-Process` launch no longer consumes a slot indefinitely,
   - ordinary commands still retain their final stdout.

## Production status

Production remains v0.4.1. The terminal lifecycle change in this document has **not** been loaded by the production Node process yet.
