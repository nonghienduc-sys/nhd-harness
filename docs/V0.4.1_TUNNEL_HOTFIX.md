# v0.4.1 Tunnel Hotfix

Date: 2026-09-13

## Incident

Production named tunnel `chatgpt-workstation-mcp` was observed exiting repeatedly while the local MCP service remained healthy. Audit records showed at least two unexpected stops with Windows exit code `4294967295` (`-1`). The previous tunnel implementation cleared its process state on exit but did not schedule recovery, so a transient `cloudflared` failure left the public MCP endpoint offline until a manual restart.

A second configuration issue was found: the persisted `cloudflaredPath` pointed at a ChatCode-owned runtime even though this project already ships its own binary. The two binaries were identical at diagnosis time, so this was not the direct cause of the observed exits, but it created an unnecessary lifecycle dependency.

## Changes in v0.4.1

### Tunnel watchdog

`src/tunnel.ts` now tracks owner intent separately from process state:

- `desiredRunning=true` only while the owner expects the tunnel to stay online.
- Unexpected process close/error schedules an automatic restart.
- Restart delays are bounded: `2s, 5s, 10s, 30s, 60s, 120s, 300s`.
- Backoff resets after a stable connection interval.
- Manual Stop, Emergency Stop and intentional application shutdown suppress automatic recovery.
- A restart timer is never duplicated while another retry/process is active.

### Diagnostics

The service now retains a bounded stdout/stderr tail and audits:

- tunnel start,
- successful registration,
- unexpected stop,
- process error,
- scheduled restart,
- stable recovery,
- explicit stop request.

This ensures a future tunnel failure keeps the useful `cloudflared` context instead of recording only an exit code.

### Runtime ownership

`src/config.ts` now migrates a persisted legacy ChatCode `cloudflaredPath` to the MCP-owned binary when `runtime\cloudflared.exe` is available. Production therefore no longer depends on ChatCode's installation lifecycle.

### cloudflared upgrade

Production binary was upgraded from `2026.8.2` to `2026.9.1`.

## Validation before production cutover

The hotfix was compiled to the isolated `dist-tunnel-stage` directory. Production `dist`, server, tunnel and dashboard remained untouched during development/testing.

Regression tests included:

- crashed process automatically restarts,
- retry delay increases after repeated failures,
- manual Stop suppresses restart,
- Emergency Stop suppresses restart,
- existing filesystem, terminal, Office, Skills, Screen, Desktop, Intake, PDF, project-memory and document-edit tests remain green.

Tunnel staging regression result: 26 tests passed, 0 failed.

A separate staging server health check on port `39110` returned version `0.4.1` while keeping its tunnel disabled.

## Production cutover

Cutover completed at approximately 12:07 local time on 2026-09-13 using `scripts\v041-cutover.ps1`.

The script performs:

1. preflight/hash/version validation,
2. full backup of production `dist`, package manifests, `cloudflared.exe` and persisted config,
3. controlled runtime stop,
4. staged file replacement,
5. runtime restart,
6. local health verification,
7. tunnel Online verification,
8. automatic rollback if any required step fails.

Post-cutover verification showed:

- `restartAttempt=0`,

## Production safety rule

Do not deliberately kill the production tunnel merely to prove the watchdog. Crash/recovery behavior is covered by injected-process regression tests in staging. Production should be tested only through passive health/audit observation unless a controlled maintenance window is explicitly approved.
