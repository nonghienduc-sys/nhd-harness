## Why v0.8.1 exists

v0.8 introduces durable long-running task state.

A restart recovery operation may mutate durable task state:

- a run in `running` / `waiting_confirmation` is changed to `paused`,
- an active step is changed to `interrupted`,
- the interrupted action is never replayed automatically.

That mutation is valid only when the new Workstation MCP process has successfully taken ownership of the HTTP listener.

If a second/non-owner process starts while the real server still owns the port, or startup fails before listener ownership, that failed process must **not** pause/interupt the real runtime's durable tasks.

## v0.8.1 safety invariant

`taskRuns.recoverAfterRestart()` executes **inside the successful `app.listen(...)` callback only**.

Therefore:

1. process starts,
2. HTTP listener binds successfully,
3. process is now the runtime owner,
4. only then durable restart recovery runs,
5. recovery is audited as `task_runtime / restart_recovery`,
6. tunnel startup follows.

A process that fails to bind must exit/fail without modifying durable task state.

A blocked tool invocation is not a failed regression test; it is an unavailable execution path. Do not claim the hotfix was tested or deployed solely because test files/candidate files exist.
