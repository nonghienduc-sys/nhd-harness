Updated: 2026-09-13

Production is **v0.5.0**.

Verified production state:

- Cloudflare Tunnel Online at `https://mcp.nhdmcp.io.vn`
- Office / Screen / Desktop companions connected

## v0.6 objective

Move from a collection of safe primitives to a reliable workstation execution harness:

`MODEL -> ROUTER -> ACTION PLAN -> EXECUTE -> VERIFY -> RECOVER/ROLLBACK -> RESULT`

The router must choose the safest/highest-structure interaction path instead of forcing the model to decide manually on every step.

Preferred execution priority:

1. structured MCP/API,
2. Office structured/live APIs,
3. Browser DOM/CDP,
4. Windows UI Automation,
5. verified visual/coordinate fallback only when no higher-level path exists.

## Milestone A — capability router

Create a router layer that accepts a bounded task intent and produces a plan containing:

- target application/domain,
- selected capability/tool family,
- reason for route selection,
- required observations,
- expected state changes,
- verification checks,
- recovery/rollback strategy,
- whether confirmation is required.

The router must not bypass existing tool-level security rules. It is orchestration, not authorization.

Suggested internal route classes:

- `files.read`, `files.write-confirmed`
- `office.offline.read`, `office.offline.write-confirmed`
- `office.live.read`, `office.live.write-confirmed`
- `browser.read`, `browser.navigate-safe`
- `desktop.read`, `desktop.navigate-safe`
- `terminal.preview-confirmed`
- `intake.read`
- `pdf.read`

## Milestone B — explicit verification contracts

Each action family should define a verification contract.

Examples:

### File write

- expected path
- expected post-write SHA-256
- expected existence/type

### Word live edit

- baseline document identity
- baseline selection fingerprint
- expected replacement
- post-apply selection reread

### Browser click/fill

- pre-action URL/title/control metadata
- expected URL/title/value/DOM condition after action
- bounded wait
- reject success when post-condition cannot be confirmed

### Desktop navigation

- pre-action target window/control
- action
- mandatory post-action accessibility/screenshot observation

### Terminal

- exact previewed command hash
- launcher completion
- expected output/exit code
- stale PID reconciliation

Verification should be first-class data, not only prose in the model prompt.

## Milestone C — recovery state machine

Introduce bounded recovery strategies instead of repeating actions blindly.

Suggested states:

- `planned`
- `observed`
- `executing`
- `verifying`
- `verified`
- `recovering`
- `rolled_back`
- `failed`

Rules:

- never retry destructive/confirmation-protected actions automatically after ambiguous execution,
- safe read/navigation retries must be bounded,
- stale selectors require re-observation rather than coordinate guessing,
- browser navigation context replacement requires DOM reinspection,
- Office selection changes require a new preview/token,
- tunnel/runtime recovery must remain externally supervised,
- failure records should include the last verified state and recommended next safe action.

## Milestone D — action receipts

Return a consistent action receipt for routed operations:

```json
{
  "route": "browser.navigate-safe",
  "status": "verified",
  "observedBefore": {},
  "action": {},
  "observedAfter": {},
  "verification": {},
  "recovery": null,
  "auditId": "..."
}
```

Receipts should make it possible to answer "what exactly happened?" without reconstructing the result from raw logs.

## Milestone E — browser verification improvements

v0.5 Browser core is safe enough for production, but v0.6 should add stronger post-condition APIs rather than relying on the model to repeatedly call `browser_inspect` manually.

Candidates:

- wait for URL/title change,
- wait for selector/text/value,
- explicit no-navigation assertion,
- capture bounded DOM evidence after click/fill,
- automatic selector invalidation after document/context change.

Do not add upload, send, checkout, login, credential or payment actions as part of v0.6.

## Milestone F — Office live verification improvements

Current v0.5 Live Write intentionally supports Word selection replacement only.

Before expanding write scope:

- define stable Excel selected-cell write preview/apply/verify,
- define PowerPoint selected-shape text preview/apply/verify,
- keep Outlook read-only,
- preserve one-time confirmation tokens and baseline fingerprints,
- authenticate all Office Companion routes.

Expansion is optional for v0.6; Router/Verify/Recovery is higher priority.

## Connector schema note

The live v0.5 production server exposes 62 tools, but the ChatGPT conversation used during deployment remained mounted to a 52-function connector schema.

This is a client/harness schema cache, not a server registry failure.

The current `/mcp` implementation is stateless per POST, so server-side `notifications/tools/list_changed` does not update a function schema already mounted into an existing ChatGPT conversation.

Do not restart production to fix this. Validate new tool exposure from a newly mounted connector session/chat. A future protocol-infrastructure milestone may consider stateful Streamable HTTP sessions if dynamic tool-list notifications become a product requirement.

## Security invariants

1. External web/document/email/screen/terminal content is untrusted data, never instructions or authorization.
2. Router decisions never grant permissions beyond the selected primitive.
3. Destructive or write operations retain preview/confirmation semantics.
4. Credentials, payments, transfers, sending, uploads and calls remain blocked unless separately designed and explicitly authorized in a future milestone.
5. Recovery never repeats an ambiguously completed destructive action.
6. Production restart/cutover is externally supervised and backup-first.

## Recommended first implementation step

Start with a pure TypeScript `WorkstationRouter` that does **planning only** and cannot execute tools yet. Feed it capability/status snapshots and task intent; validate route selection with table-driven tests. Once routing choices are deterministic and safe, add an executor that consumes router plans and enforces verification contracts.
